# Project Rules

## 项目定位

`{{PROJECT_NAME}}` 是一个 `{{PROJECT_TYPE}}` 项目，核心目标是：

- `{{PRIMARY_GOAL_1}}`
- `{{PRIMARY_GOAL_2}}`
- `{{PRIMARY_GOAL_3}}`

## 技术边界

- 技术栈：`{{TECH_STACK}}`
- 平台：`{{PLATFORMS}}`
- 构建/包管理：`{{BUILD_SYSTEM}}`

默认不引入新依赖，除非收益明确且维护成本可接受。

## 实现原则

1. 优先保留项目既有结构与风格。
2. 优先做最小可验证改动。
3. 新增状态、流程或模块时，职责必须清晰。
4. 真实使用体验优先于演示效果。
5. 涉及系统交互、权限、网络、存储或关键业务流程时，必须考虑失败路径。

## 代码修改规则

1. 未经明确需求，不要扩大任务范围。
2. 不要为了“顺手优化”而改动无关模块。
3. 改动应尽量与当前任务直接相关。
4. 如果引入新的结构或约定，必须同步更新文档。

## 验证规则

在可行的情况下，优先执行：

- `{{PRIMARY_BUILD_COMMAND}}`
- `{{PRIMARY_TEST_COMMAND}}`

如果改动涉及核心交互，还应补充人工验证。

## 文档规则

以下情形应更新文档：

- 项目目标或范围变化
- 目录结构或模块职责变化
- 任务状态变化
- 会影响下一次会话接手的信息变化

最常更新的文档：

- `docs/ai-context.md`
- `docs/architecture.md`
- `docs/todo.md`
- `docs/dev-log.md`

## Git 规则

人工分支建议：

- `feature/<task>`
- `fix/<task>`

如果由 Codex 代为创建分支，遵循当前工作环境要求：

- `codex/<task>`
